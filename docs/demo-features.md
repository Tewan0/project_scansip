# การเสิร์ฟ รับเงิน และ AI ฝั่งลูกค้า

อัปเดต 21 ตุลาคม 2026 — ผู้ใช้ยืนยันว่าลิงก์ Vercel เวอร์ชันก่อนหน้านี้ใช้งานได้แล้ว งานชุดนี้ต้องนำโค้ดใหม่ขึ้น Vercel อีกครั้งจึงจะปรากฏบนลิงก์นั้น

## ลำดับสาธิต

1. หน้าร้านเปิดโต๊ะ แล้วลูกค้าสแกน QR
2. ลูกค้ากด **ถาม AI ช่วยเลือกเมนู** ถามความชอบหรืองบประมาณ แล้วเลือกเพิ่มเมนูแนะนำในตะกร้า
3. ลูกค้าเปิดตะกร้า ตรวจรายการและส่งออเดอร์เอง สามารถสั่งเพิ่มได้โดยยังอยู่ในบิลเดิม
4. ครัวกดเริ่มทำและทำเสร็จ หน้าลูกค้าจะแสดงทำเสร็จแล้ว / รอเสิร์ฟ
5. หน้าร้านเปิดรายการสั่งในบิล นำอาหารไปถึงโต๊ะ แล้วกด **เสิร์ฟแล้ว · ครบออเดอร์นี้**
6. รับเงินรวมทั้งบิล เลือกเงินสดหรือโอน/พร้อมเพย์ เงินสดกรอกยอดรับ ระบบคำนวณเงินทอน ส่วนเงินโอนต้องตรวจบัญชีร้านแล้วติ๊กยืนยัน
7. ปิดโต๊ะเมื่อรับเงิน ทำอาหาร และเสิร์ฟครบ จากนั้นเปิดรอบใหม่เพื่อตรวจว่าบิลและ QR แยกจากรอบเดิม

การเสิร์ฟเป็นรายออเดอร์ (แต่ละครั้งที่ลูกค้ากดสั่ง) ยังไม่แยกการเสิร์ฟรายจานหรือบางจำนวนในบรรทัดเดียว

## การรับเงินและข้อมูลเก่า

- รับเงินก่อนครัวทำเสร็จได้ แต่ยังปิดโต๊ะไม่ได้จนเสิร์ฟครบ
- ยืนยันเสิร์ฟได้เฉพาะเจ้าของร้านหรือหน้าร้าน หลังครัวทำอาหารครบออเดอร์ ครัวไม่มีสิทธิ์ยืนยันเสิร์ฟหรือรับเงิน
- ออเดอร์ที่เสิร์ฟแล้วหรือรับเงินแล้วไม่สามารถยกเลิกด้วยปุ่มยกเลิกออเดอร์ ระบบยังไม่มีขั้นตอนคืนเงิน
- ทุกครั้งที่รับเงินสร้างรายการ `bill_payments` และเชื่อมออเดอร์ที่ชำระเข้ากับรายการนั้น เก็บช่องทาง ยอดบิล ยอดรับ เงินทอน ผู้รับเงิน และเวลา
- ยอดคิดเป็นสตางค์และตรวจซ้ำที่เซิร์ฟเวอร์ เงินสดไม่พอหรือยอดโอนไม่ตรงจะไม่ถูกบันทึก หากมีการสั่งเพิ่ม/ยกเลิก/รับเงินระหว่างตรวจบิล ต้องเปิดยอดล่าสุดและยืนยันใหม่
- บิลแสดงประวัติรับเงิน รองรับการรับเงินแล้วสั่งเพิ่มในรอบเดิม ออเดอร์เก่าที่รับเงินไปก่อนมีระบบนี้ไม่มีช่องทางรับเงินย้อนหลังที่แต่งขึ้น
- ออเดอร์เดิมไม่ถูกบังคับให้ยืนยันเสิร์ฟย้อนหลังและไม่สร้างเวลาเสิร์ฟปลอม API ใหม่กำหนด `servingRequired=true` เมื่อสร้างออเดอร์ ส่วนค่าเริ่มต้นฐานข้อมูลเป็น false เพื่อให้ deployment เก่ายังใช้งานได้ระหว่างอัปเดต

## เปิดใช้งาน AI

อัปเดต 23 ตุลาคม 2026: เปลี่ยนตัวเชื่อมต่อเป็น Gemini อ่าน `GEMINI_AI_API_KEY` และใช้ `GEMINI_MODEL` (ไม่บังคับ; ค่าเริ่มต้น `gemini-3.5-flash-lite`) ต้องตั้งค่าคีย์ชื่อเดียวกันบน Vercel แล้ว deploy โค้ดใหม่ การทดสอบจากเครื่องพัฒนากับ Google จริงด้วยเมนูจำลองหนึ่งรายการได้ HTTP 200 และคืน ID เมนูที่ถูกต้อง ผ่านชุดทดสอบ AI จำลอง 8 กรณี ยังไม่ได้ตรวจบน Vercel

เพิ่มค่าต่อไปนี้ใน `.env.local` สำหรับเครื่องพัฒนา และใน Environment Variables ของโปรเจกต์ Vercel ที่ใช้สาธิต แล้ว redeploy:

```dotenv
GEMINI_AI_API_KEY=ใส่คีย์จริงในระบบตั้งค่าเท่านั้น
GEMINI_MODEL=gemini-3.5-flash-lite
```

ห้ามใส่ key ในโค้ด Git หรือชื่อที่ขึ้นต้นด้วย `NEXT_PUBLIC_` ไม่ต้องส่ง key ในแชต ไฟล์ `.env.example` เว้นช่อง key ว่างไว้โดยตั้งใจ

ตัวเชื่อมต่อใช้ Google Gemini generateContent API ผ่านฝั่งเซิร์ฟเวอร์และ Structured Outputs ไม่มีการสมัครหรือซื้อเครดิตให้อัตโนมัติ ต้องใช้ key ของบัญชี API ที่เรียกโมเดลที่ตั้งค่าได้ การใช้งานจริงเป็นไปตามเงื่อนไขและค่าใช้จ่ายของผู้ให้บริการ

- อ่านเมนูที่ยังขายอยู่ของร้านจาก QR ปัจจุบัน สูงสุด 80 รายการ เรียงตามชื่อ ส่งชื่อ คำอธิบายที่ตัดความยาว ราคา และ ID พร้อมบทสนทนาล่าสุดให้ AI
- ไม่ส่ง QR token, API key, อีเมลพนักงาน, รายรับ หรือออเดอร์ของลูกค้าคนอื่นไปกับ prompt
- รับคำตอบแบบข้อความและ ID เมนู จากนั้นกรอง ID ให้เป็นเมนูที่มีอยู่ในข้อมูลร้านจริง ชื่อและราคาบนการ์ดมาจากฐานข้อมูล ไม่ใช้ราคาที่ AI แต่ง
- AI ไม่มีเครื่องมือเปลี่ยนข้อมูลร้าน สั่งอาหาร รับเงิน หรือเรียกพนักงาน ลูกค้าต้องกดเพิ่มตะกร้าและส่งออเดอร์เอง
- คำตอบข้อความของ AI อาจคลาดเคลื่อน โดยเฉพาะส่วนผสมและสารก่อภูมิแพ้ ต้องยืนยันกับพนักงาน
- ไม่เก็บข้อความแชตในฐานข้อมูลแอป ประวัติในหน้าจออยู่ในหน่วยความจำและหายเมื่อรีเฟรช การจัดเก็บและใช้ข้อมูลฝั่ง Google เป็นไปตามเงื่อนไขบริการ Gemini โดย Free Tier อาจใช้ข้อมูลเพื่อปรับปรุงผลิตภัณฑ์
- จำกัดคำถามห่างกัน 5 วินาที, 40 ครั้งต่อรอบโต๊ะ และ 100 ครั้งต่อร้านต่อวันตามเวลาไทย เก็บตัวนับใน PostgreSQL จึงแชร์ระหว่าง Vercel instances ตัวนับรวมการเรียกที่ผู้ให้บริการตอบล้มเหลวเพื่อจำกัดการใช้ซ้ำ
- จำกัดประวัติส่งไป AI ไม่เกิน 9 ข้อความ ข้อความละ 1,200 ตัวอักษร และคำขอรวม 24 KB รอผู้ให้บริการไม่เกิน 20 วินาที
- ตรวจ QR ก่อนเรียก AI และตรวจซ้ำหลังตอบเสร็จ หากโต๊ะถูกปิดระหว่างรอจะไม่แสดงคำตอบของรอบเก่า
- หากยังไม่ใส่ key หรือบริการผิดพลาด จะแจ้งว่า AI ยังไม่พร้อม ไม่แสดงคำตอบจำลองว่าเป็น AI ลูกค้ายังเลือกเมนูและสั่งอาหารได้ตามปกติ

เอกสารผู้ให้บริการ: [Structured Outputs](https://ai.google.dev/gemini-api/docs/generate-content/structured-output)

## ฐานข้อมูลและการตรวจสอบ

- Drizzle สร้าง `0005_service_payments_customer_ai.sql`, `0006_order_receipt_index.sql` และ `0007_serving_rollout_compatibility.sql`
- ใช้กับ Project ScanSip แล้วเมื่อ 21 ตุลาคม 2026: ไฟล์ 0005 และ 0006 รวมใน migration `20261021044732_service_payments_customer_ai`; 0007 อยู่ใน `20261021045108_serving_rollout_compatibility` ห้ามรันไฟล์เดิมซ้ำบนโปรเจกต์นี้
- ตารางใหม่เปิด RLS และถอนสิทธิ์ anon/authenticated/PUBLIC ใช้ผ่าน API ที่ตรวจสิทธิ์ของเซิร์ฟเวอร์เท่านั้น มี index สำหรับอ่านประวัติรับเงินและ FK ของออเดอร์
- ตรวจข้อกำหนดรับเงินในฐานข้อมูลจริงด้วยข้อมูลชั่วคราวใน transaction แล้ว rollback ทั้งหมด ไม่สร้างบิลรับเงินจริงเพื่อทดสอบ
- ผลตรวจ 21 ตุลาคม 2026: ผ่าน 95 tests, `npx tsc --noEmit`, ESLint ของไฟล์ที่แก้ และ `git diff --check` ชุดทดสอบมีฐานข้อมูลและ AI provider จำลอง จึงยังต้องทดสอบคำตอบ AI จริงหลังตั้ง key รวมถึงหน้าจอมือถือบน deployment ใหม่ ผล production build ของโค้ดชุดใหม่นี้ยังไม่ได้ตรวจบน Vercel
- ผล Advisor ตารางใหม่เป็น [RLS Enabled No Policy](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy) ระดับ INFO ตามรูปแบบ backend-only คำเตือนเดิมเรื่อง [สิทธิ์ฟังก์ชัน](https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable) และ [การป้องกันรหัสผ่านรั่ว](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection) ยังเป็นรายการค้างเดิม ไม่ได้แก้ในงานฟีเจอร์นี้
