# ตะกร้าลูกค้า

## ป้องกันออเดอร์ซ้ำเมื่อเครือข่ายขัดข้อง

- ก่อนส่ง สร้าง `requestId` และบันทึกพร้อมตะกร้า การลองส่งใหม่หรือรีเฟรชจะใช้รหัสเดิมจนยืนยันผลสำเร็จ
- ระหว่างที่ยังไม่ทราบผล จะล็อกการแก้รายการและแสดงปุ่ม “ตรวจสอบการส่งอีกครั้ง” เพื่อป้องกันส่งข้อมูลคนละชุดด้วยรหัสเดียวกัน
- API ตรวจรอบ QR ก่อนคืนออเดอร์เดิม โดยไม่สร้างรายการเพิ่ม แม้เมนูเดิมถูกลบ หมด หรือเปลี่ยนราคาแล้ว หากใช้รหัสเดิมแต่เปลี่ยนรายการจะตอบ 409
- เมื่อคำขอถูกปฏิเสธแน่นอนด้วย 400/403/404 จะปล่อยรหัสให้แก้ไขตามสถานะ ส่วนเครือข่ายขัดข้องหรือข้อผิดพลาดเซิร์ฟเวอร์จะเก็บรหัสไว้
- หลังส่งสำเร็จจะล้างตะกร้า การสั่งครั้งถัดไปได้รหัสใหม่ จึงยังสั่งอาหารรายการเดิมเพิ่มเติมได้
- ดัชนี unique แยกตามร้าน โต๊ะ รอบ QR และรหัสส่งคำขอ ร่วมกับ transaction lock ป้องกันคำขอรหัสเดียวกันเข้าพร้อมกัน
- ลูกค้า API รุ่นเก่าที่ไม่ส่ง `requestId` ยังสั่งได้ แต่ไม่ได้รับการป้องกันนี้ หากเบราว์เซอร์บันทึกไม่ได้ รหัสคงอยู่เฉพาะหน้าเดิม จึงควรหลีกเลี่ยงการรีเฟรชตามคำเตือน

Migration `drizzle/0008_order_idempotency.sql` เพิ่มคอลัมน์ nullable สองคอลัมน์และดัชนี โดยใช้กับ Project ScanSip แล้ววันที่ 22 ตุลาคม 2026 ผ่าน Supabase migration `order_idempotency` ไม่ควรรัน SQL นี้ซ้ำกับฐานข้อมูลนั้น ส่วนฐานข้อมูลอื่นต้องใช้ migration ก่อนนำโค้ดใหม่นี้ขึ้นระบบ การแก้ไขแอปยังไม่ได้ deploy

ทดสอบระดับ component/handler ครอบคลุมผลตอบกลับสูญหาย การรีเฟรช เมนูหายระหว่างลองส่งใหม่ การเปลี่ยนข้อมูลด้วยรหัสเดิม ขอบเขตร้าน/โต๊ะ/รอบ QR และเบราว์เซอร์ที่ปิดกั้น storage พร้อมทดสอบ unique constraint บนฐานข้อมูลด้วยข้อมูลชั่วคราวและ rollback ทั้งหมด การทดสอบเหล่านี้ยังไม่ใช่การตรวจหน้าจอบนเบราว์เซอร์จริง

- เปิดตะกร้าได้จากปุ่มด้านบนและแถบด้านล่าง แม้ยังไม่มีรายการ
- บันทึกรายการ จำนวน หมายเหตุรายเมนู และข้อความถึงครัวทันทีในเบราว์เซอร์เดิม โดยแยกตามร้าน โต๊ะ และรอบ QR
- รีเฟรชแล้วดึงราคาและสถานะเมนูปัจจุบันมาใช้ เมนูที่ถูกลบหรือหมดจะยังแสดงให้ลูกค้านำออกก่อนส่ง
- ส่งไม่สำเร็จจะเก็บตะกร้าไว้ ส่งสำเร็จจะล้างตะกร้า รวมถึงเมื่อระบบยืนยันว่าโต๊ะปิดหรือ QR หมดอายุ
- ถ้าเบราว์เซอร์ปิดกั้นการบันทึก จะแจ้งเตือนให้หลีกเลี่ยงการรีเฟรชก่อนส่งออเดอร์

## วิธีทดสอบด้วยมือถือ

1. เปิด QR ของโต๊ะที่กำลังใช้งาน แล้วเปิดตะกร้าขณะว่าง
2. เพิ่มเมนู ปรับจำนวน ใส่หมายเหตุรายเมนูและข้อความถึงครัว
3. รีเฟรชหน้า: รายการ จำนวน และข้อความต้องกลับมาเหมือนเดิม
4. เปิดตะกร้าอีกครั้งแล้วลองลดจำนวนและนำรายการออก
5. ส่งออเดอร์ทดสอบ: เมื่อสำเร็จ ตะกร้าต้องว่างและรีเฟรชแล้วต้องไม่กลับมา
6. ปิดและเปิดโต๊ะรอบใหม่: QR ใหม่ต้องไม่ดึงตะกร้าของรอบเก่ามาใช้

ตะกร้าไม่แชร์ข้ามเครื่องหรือเบราว์เซอร์ และการเปลี่ยนโดเมน/พอร์ตของเว็บถือเป็นพื้นที่บันทึกคนละชุด ประวัติออเดอร์หลังส่งเป็นคนละส่วนกับตะกร้า

## ประวัติและคำขอพนักงาน

- หน้าลูกค้าโหลดออเดอร์ทั้งหมดจากฐานข้อมูลเฉพาะร้าน โต๊ะ และรอบ QR ที่ยังเปิดอยู่ ทุกคนที่ใช้ QR รอบเดียวกันเห็นประวัติเดียวกัน รีเฟรชหรือสแกนซ้ำในอีกเครื่องแล้วประวัติยังอยู่
- สถานะรายเมนูแสดงรอทำ / กำลังทำ / ทำเสร็จแล้ว ตามที่ครัวปรับ ออเดอร์ที่ยกเลิกแสดงยกเลิกและไม่รวมในยอดชำระ
- สถานะออเดอร์ `served` หมายถึงครัวทำเสร็จ จึงแสดง “ทำเสร็จแล้ว / รอเสิร์ฟ” เมื่อหน้าร้านยืนยันเสิร์ฟครบออเดอร์จะแสดง “เสิร์ฟแล้ว” แยกจากสถานะครัว ดูขั้นตอนล่าสุดใน [คู่มือสาธิต](demo-features.md)
- ประวัติแสดงยอดรวมรอบโต๊ะและยอดที่ยังไม่ชำระ พร้อมเพย์ใช้ยอดที่ยังไม่ชำระของทั้งรอบ ควรตรวจยอดกับพนักงานก่อนโอน
- ปุ่มเรียกพนักงานและขอเช็กบิลส่งคำขอแยกประเภท ขณะมีคำขอรออยู่จะกดซ้ำไม่ได้ และฝั่งเซิร์ฟเวอร์คืนคำขอเดิมเมื่อได้รับคำขอซ้ำ
- หน้าผังโต๊ะและออเดอร์หน้าร้านมีแผง “คำขอจากลูกค้า” พนักงานกด “ดำเนินการแล้ว” หลังช่วยลูกค้า การกดนี้ไม่ยืนยันรับเงินหรือปิดโต๊ะ
- ทั้งประวัติและคำขออัปเดตทุก 5 วินาที มีปุ่มอัปเดตเอง ถ้าเชื่อมต่อล้มเหลวจะเก็บรายการเดิมและแจ้งข้อผิดพลาด
- ปิดโต๊ะแล้วคำขอที่ค้างในรอบนั้นจะสิ้นสุด QR เก่าอ่านประวัติหรือเรียกพนักงานไม่ได้ รอบใหม่เริ่มประวัติใหม่

### ลองใช้งานสองหน้าจอ

1. เปิดโต๊ะจากหน้าพนักงาน สแกน QR แล้วส่งออเดอร์สองครั้งจากหน้าลูกค้า
2. รีเฟรชหน้าลูกค้า: ต้องเห็นทั้งสองออเดอร์ พร้อมหมายเหตุและยอดรวม
3. ฝั่งครัวกดเริ่มทำและทำเสร็จเฉพาะหนึ่งรายการ: ลูกค้าต้องเห็นสถานะของรายการนั้นเปลี่ยนภายในรอบอัปเดต
4. ลูกค้ากดเรียกพนักงาน: หน้าพนักงานต้องเห็นหมายเลขโต๊ะและประเภทคำขอ กดดำเนินการแล้วและตรวจว่าหน้าลูกค้าแสดงผลตาม
5. ลองขอเช็กบิล: ต้องมีคำขอในหน้าพนักงาน แต่ยอดยังไม่ถูกบันทึกว่าชำระแล้วจนกว่าพนักงานจะรับเงิน
6. ทำออเดอร์ให้เสร็จ รับเงิน และปิดโต๊ะตามปกติ: QR เก่าต้องใช้งานไม่ได้ และ QR ของรอบใหม่ต้องไม่มีประวัติหรือคำขอเดิม

### รับเงินก่อนปิดโต๊ะ

จากผังโต๊ะ กด “ตรวจออเดอร์ / รับเงิน” เพื่อเปิด **บิลหน้าร้าน** หน้าจะเริ่มที่ “รอบปัจจุบัน” กด “รับเงินรวมทั้งบิล” แล้วตรวจเลขโต๊ะ เลขบิล เวลาเริ่มรอบ จำนวนออเดอร์และยอดเงิน เลือกเงินสดและกรอกยอดรับเพื่อคำนวณเงินทอน หรือเลือกโอนและยืนยันว่าตรวจเงินเข้าแล้ว ก่อนกด “ยืนยันว่าได้รับเงินแล้ว” สำหรับออเดอร์ใหม่ ต้องทำอาหารและยืนยันเสิร์ฟครบด้วยจึงจะปิดโต๊ะได้ รับเงินก่อนเสิร์ฟได้โดยไม่ข้ามขั้นตอนอาหาร

แก้ไขวันที่ 20 ตุลาคม 2026 หลังพบว่าหน้าร้านไม่มีปุ่มบันทึกรับเงิน ทั้งที่ API รองรับอยู่แล้ว ตรวจ flow รับเงินสองออเดอร์ รวม 170 บาท → แจ้งยอดคงเหลือ → ปิดโต๊ะเมื่อครบ และตรวจกรณีรับเงินแล้วแต่อาหารยังไม่เสร็จด้วยข้อมูลจำลอง โดยไม่เปลี่ยนสถานะเงินของออเดอร์จริง

### หนึ่งรอบเปิดโต๊ะต่อหนึ่งบิล

- การกดสั่งเพิ่มอยู่ใต้บิลของรอบ QR เดิม กด “ดูรายการสั่ง” เพื่อดูครั้งที่ 1, 2, 3 พร้อมเวลา หมายเหตุ และสถานะรายเมนู ยกเลิกแต่ละครั้งที่ยังไม่รับเงินได้จากส่วนนี้
- บิลที่รับเงินครบยังอยู่ในรอบปัจจุบันจนกว่าจะปิดโต๊ะ เมื่อเปิดโต๊ะใหม่จะได้บิลใหม่ บิลเก่าย้ายไป “ประวัติบิล” กรองด้วยเลขโต๊ะและวันที่ได้
- เลขบิลสร้างแบบคงที่จากร้าน เลขโต๊ะ และรหัสรอบ โดยไม่ส่งรหัส QR ให้หน้าบิลหรือครัว บิลเก่าที่ไม่มีรหัสรอบจะคงแยกตามออเดอร์ ไม่เดารอบจากเวลา
- สำหรับรอบเก่าที่ไม่มีเวลาเปิดโต๊ะ แสดง “สั่งครั้งแรก” ตามเวลาออเดอร์แรก ส่วนรอบที่กำลังใช้งานแสดงเวลาเปิดโต๊ะ
- หน้าครัวยังแยกเป็นใบงานแต่ละครั้งที่สั่ง และแสดงเลขบิลเดียวกับหน้าร้าน
- รับเงินรวมเฉพาะออเดอร์ที่ยังไม่ได้รับเงิน ไม่นับรายการยกเลิกหรือคืนเงิน หากมีการสั่งเพิ่ม ยกเลิก หรือรับเงินไปก่อนแล้วระหว่างตรวจยอด ระบบตอบ 409 โดยไม่บันทึกบางส่วน และให้ตรวจยอดใหม่
- API อ่านข้อมูลสรุปออเดอร์ให้ครบก่อนแบ่งหน้า (20 บิลต่อหน้า) และโหลดรายละเอียดเมนูเฉพาะบิลที่แสดง จึงไม่ตัดยอดของบิลที่มีการสั่งหลายครั้งตามขีดจำกัดจำนวนออเดอร์เดิม
- ทดสอบบนเครื่อง: เปิดโต๊ะ สั่งสองครั้ง ต้องเห็นบิลเดียว; รับเงินรวมแล้วบิลยังเป็นรอบปัจจุบัน; ปิดและเปิดโต๊ะใหม่ ต้องได้เลขบิลใหม่และพบเลขเดิมในประวัติ

การปรับบิลใช้ข้อมูลรอบโต๊ะที่มีอยู่ ไม่ต้องเปลี่ยน schema หรือแก้ยอด/สถานะเงินของข้อมูลเดิม ตรวจข้อมูลร้าน zzzq วันที่ 20 ตุลาคม 2026 พบโต๊ะ 6 มี 5 ออเดอร์ใน 3 รหัสรอบ จึงแสดง 3 บิลตามข้อมูลจริง

ฐานข้อมูลใช้ `drizzle/0004_customer_service_requests.sql` (สร้างด้วย Drizzle Kit) และนำไปใช้ใน Project ScanSip แล้ววันที่ 20 ตุลาคม 2026 เปิด RLS และถอนสิทธิ์ Data API ของ anon/authenticated/PUBLIC; เข้าถึงผ่าน API ที่ตรวจ QR หรือสิทธิ์เจ้าของร้าน/หน้าร้านเท่านั้น มี unique index กันคำขอค้างซ้ำและตรวจชนิดคำขอที่ฐานข้อมูล

Advisor แสดง [RLS Enabled No Policy](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy) ระดับ INFO สำหรับตารางใหม่นี้ตามรูปแบบที่ปิด Data API โดยตั้งใจ ส่วนคำเตือนเดิมบันทึกไว้ใน `docs/roles-and-kitchen.md`

## ผลตรวจอัตโนมัติ

วันที่ 20 ตุลาคม 2026: ผ่าน 78 tests รวมตะกร้า ประวัติ การแยกร้าน/โต๊ะ/รอบ QR สิทธิ์พนักงาน คำขอซ้ำ การปิดรอบ และปุ่มในหน้าลูกค้า/พนักงาน; TypeScript และ ESLint ของไฟล์ใหม่ผ่าน ตรวจ RLS/grants/indexes ของฐานข้อมูลจริงแล้ว และทดสอบ constraint กันคำขอซ้ำ/ชนิดคำขอ/การส่งใหม่หลังดำเนินการ โดย rollback ข้อมูลทดสอบทั้งหมด การทดสอบหน้าเว็บใช้ตัวจำลอง component/handler ยังต้องตรวจการแสดงผลบนมือถือจริงตามขั้นตอนข้างต้น
