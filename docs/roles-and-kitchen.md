# สิทธิ์ผู้ใช้และหน้าครัว

## การใช้งาน

1. เจ้าของร้านเปิด **จัดการพนักงาน** (`/dashboard/staff`) แล้วเพิ่มอีเมล Google และเลือกหน้าร้านหรือครัว การเพิ่มรายชื่อไม่ได้ส่งอีเมลเชิญอัตโนมัติ
2. พนักงานเข้า `/owner/login` และใช้บัญชี Google ที่เจ้าของร้านเพิ่ม ระบบอ่านบทบาทจากฐานข้อมูลและส่งไปหน้าทำงาน
3. เจ้าของร้านใช้เมนู **ช่วยงานหน้าร้าน** หรือ **ช่วยงานครัว** ได้ทันทีโดยไม่ต้องเข้าสู่ระบบใหม่
4. ครัวกด **เริ่มทำ** / **ทำเสร็จ** รายเมนู หรือ **ทำเสร็จทั้งหมด** ต่อออเดอร์ เมนูจำนวนหลายชิ้นในบรรทัดเดียวมีสถานะเดียวกัน
5. หน้าร้านดูสถานะและยกเลิกออเดอร์ที่ยังไม่ชำระได้ การเปลี่ยนบทบาทหรือลบพนักงานมีผลในการเรียก API ครั้งถัดไป

| งาน | เจ้าของร้าน | หน้าร้าน | ครัว |
| --- | --- | --- | --- |
| เมนู / พนักงาน / ตั้งค่าร้าน / รายงาน | ได้ | ไม่ได้ | ไม่ได้ |
| ปรับจำนวนโต๊ะ | ได้ | ไม่ได้ | ไม่ได้ |
| เปิดโต๊ะ / ดู QR / ปิดรอบที่ไม่มีงานหรือยอดค้าง | ได้ | ได้ | ไม่ได้ |
| ดูและยกเลิกออเดอร์ที่ยังไม่ชำระ | ได้ | ได้ | ไม่ได้ |
| เปลี่ยนสถานะอาหารรายเมนู | ได้ | ไม่ได้ | ได้ |

## ขอบเขตปัจจุบัน

- หน้าร้านอยู่ `/frontdesk` และ `/frontdesk/orders`; ครัวอยู่ `/kitchen`
- ออเดอร์รีเฟรชทุก 8 วินาที และผังโต๊ะทุก 10 วินาที ยังไม่ได้เชื่อม Supabase Realtime
- ค่า `served` เดิมใช้แทนอาหารทำเสร็จทั้งออเดอร์ในขั้นนี้ ยังไม่มีสถานะยืนยันว่าเสิร์ฟถึงโต๊ะแยกต่างหาก
- พิมพ์ใบ QR และระบบรวมบิล รับเงินสด/PromptPay และปิดบิล เป็นงานขั้นถัดไป API เปลี่ยนการชำระเงินรายออเดอร์เดิมยังไม่ใช่ระบบรวมบิล
- `manager` ไม่มีสิทธิ์เข้าใช้งานและเพิ่มใหม่ไม่ได้ เก็บ enum เดิมไว้รองรับข้อมูลเก่า หากพบรายชื่อเก่า เจ้าของร้านเปลี่ยนเป็นหน้าร้านหรือครัวได้
- บัญชีพนักงานที่ถูกเพิ่มในหลายร้านจะถูกปฏิเสธแทนการเลือกร้านเอง ระบบเลือกร้านสำหรับพนักงานหลายสาขายังไม่อยู่ในขอบเขต

## ฐานข้อมูลและการตรวจสอบ

- ใช้ Supabase Auth ตรวจตัวตน และ Drizzle อ่านบทบาท/ร้านจริงใน API และ Server Actions ไม่ใช้ `user_metadata` หรือ query parameter เป็นสิทธิ์
- `drizzle/0001_staff_roles_and_kitchen.sql` เพิ่มสถานะรายเมนูและปรับสถานะข้อมูลเดิมตามออเดอร์ ใช้กับ Project ScanSip แล้วเมื่อ 20 ตุลาคม 2026
- `drizzle/0002_restrict_direct_data_access.sql` **ใช้กับฐานข้อมูลจริงแล้วหลังผู้ใช้อนุมัติ** เมื่อ 20 ตุลาคม 2026 บันทึกใน Supabase migration `20261020075803_restrict_direct_data_access`: เปิด RLS ใน 7 ตาราง ถอนสิทธิ์ Data API ของ `anon`/`authenticated`/`PUBLIC` และปิดนโยบายอัปโหลดรูปเมนูสาธารณะ ตรวจยืนยัน RLS และสิทธิ์เข้าตารางแล้ว จำนวนข้อมูลก่อนและหลังเท่าเดิมทุกตาราง นโยบายอ่านรูปสาธารณะยังคงอยู่
- `drizzle/0003_unique_store_table_numbers.sql` ใช้กับฐานข้อมูลจริงเมื่อ 20 ตุลาคม 2026 เพื่อแก้ปุ่มปิดโต๊ะรายงานสำเร็จแต่ยังแสดงใช้งาน: พบเลขโต๊ะ 2–8 ของร้านเดียวกันซ้ำ จึงรวมเป็นหนึ่งแถวต่อเลขโดยเก็บรอบที่เปิดอยู่ ย้ายความสัมพันธ์ประวัติออเดอร์ก่อนนำแถวว่างซ้ำออก และเพิ่ม `UNIQUE(store_id, table_number)` หากพบหลายรอบที่เปิดอยู่ในเลขเดียวกัน migration จะหยุดโดยไม่รวมเอง API ตรวจข้อมูลซ้ำและตอบ 409 แทนการเปลี่ยนแถวผิด
- โค้ดอ่านข้อมูลผ่าน Next.js/Drizzle และอัปโหลดผ่าน Storage client ฝั่งเซิร์ฟเวอร์ ต้องมี `SUPABASE_SERVICE_ROLE_KEY` ที่ไม่ขึ้นต้นด้วย `NEXT_PUBLIC_`
- migration แรกถูกบันทึกผ่าน Supabase migration history อย่ารันไฟล์ backfill นี้ซ้ำโดยไม่ตรวจประวัติ เพราะอาจทับสถานะรายเมนูที่เปลี่ยนไปแล้ว

```sh
npm test
npm run build
npm run lint
```

ชุดทดสอบใช้ตัวจำลอง Supabase/ฐานข้อมูลเพื่อเรียก handler และ Server Action จริง ตรวจข้ามบทบาท/ข้ามร้าน การเปลี่ยนบทบาท คุกกี้หลัง OAuth และออเดอร์ครัว ไม่ใช่การล็อกอิน Google แบบ end-to-end

ผลตรวจวันที่ 20 ตุลาคม 2026: `npm test` ผ่าน 43 กรณี, `tsc --noEmit` ผ่าน และ `git diff --check` ผ่าน ส่วน build ใน environment นี้ยังไม่ผ่าน: Turbopack เริ่ม process สำหรับ CSS ไม่สำเร็จ และ Webpack ติด `EPERM` ตอนสร้าง `.next/server/app/api` จึงยังยืนยัน production build ของงานชุดนี้ไม่ได้

ก่อนสาธิต ให้ทดสอบด้วยบัญชีเจ้าของร้าน หน้าร้าน และครัวคนละบัญชี รวมถึงมือถือ/iPad ทั้งสองแนว การล็อกอินจริงและภาพบนอุปกรณ์ยังต้องตรวจเพิ่มเติม

## รายการที่ต้องจัดการก่อนใช้งานจริง

- Advisor แจ้ง `RLS Enabled No Policy` ระดับ INFO ทั้ง 7 ตาราง ซึ่งตรงกับการตั้งใจปิด Data API โดยตรงในขั้นนี้: แอปใช้ Drizzle ผ่านบทบาทฐานข้อมูลของเซิร์ฟเวอร์ และตรวจสิทธิ์ที่ API/Server Actions ดู [รายละเอียด](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy)
- `.env.example` เคยมี service-role key และรหัสฐานข้อมูลจริงในไฟล์ที่ Git ติดตาม แก้เป็น placeholders แล้ว แต่ต้องเปลี่ยนค่าลับเดิมและอัปเดต `.env.local`/ระบบ deploy การแก้ไฟล์ปัจจุบันไม่ได้ลบค่าจากประวัติ Git
- Supabase advisor ยังเตือนสิทธิ์เรียก `public.rls_auto_enable()` แบบ SECURITY DEFINER ของผู้ใช้ทั่วไป ไม่ได้แก้สิทธิ์นี้ในขั้นปัจจุบัน ดู [แนวทางแก้](https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable)
- Advisor แจ้งว่ายังไม่เปิด leaked-password protection; ฟีเจอร์นี้เกี่ยวกับบัญชีที่ใช้รหัสผ่าน ส่วน flow ปัจจุบันใช้ Google ดู [รายละเอียด](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection)
