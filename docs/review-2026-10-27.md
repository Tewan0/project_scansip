## 1. P2: Overlapping polling can discard every successful response

Affected: components/customer-session-panel.tsx (5-second interval), components/bill-board.tsx (8-second interval). The same request-version pattern exists in components/order-board.tsx and components/service-request-board.tsx.

Each read increments a version. Responses are accepted only for the latest version. Polling checks pending mutations but not pending reads. If each response takes longer than the polling interval, every new poll invalidates the previous response before it arrives. Orders/bills can remain stale or loading despite successful responses, and requests overlap.

Reproduction: an inline Node harness based on tests/service-panels.test.mjs loaded the actual CustomerSessionPanel and BillBoard with deferred fetch responses. Start a request, trigger the next poll, then resolve the earlier request successfully; repeat three times. Both components discarded all three responses. Pausing polling and resolving the newest request made the data visible. Four requests were issued per component. The other two components were identified by source review, not this reproduction.

Fix direction: serialize polling reads for the same view or schedule the next poll after completion. Preserve invalidation on filter/session changes, mutations and unmount. An outstanding read for an old view must not indefinitely block a new view. Do not simply remove version checks. Add slow-response, filter-change and mutation regression coverage. Visibility-aware polling for the customer panel is optional related housekeeping.

## 2. P2: Menu creation can delete a live image after an ambiguous insert

Affected: app/api/menu/route.ts, POST insert error handler.

The handler uploads an image, inserts a menu, and removes the image on any insert exception. A database exception can occur after a successful commit if its acknowledgement is lost. In this case a saved menu references an image that the handler deletes.

Reproduction: exercise the actual POST handler with the existing valid-image fixture and mocked database/storage dependencies. The insert records the menu then throws an acknowledgement-loss error. Observed result: HTTP 500, one saved menu, and its live image deleted. Production data was not modified.

Fix direction: verify that no menu references the new image before cleanup, and retain it when verification fails. The update action already implements this strategy in cleanupFailedMenuUpload in app/actions/menu.ts; share it with creation where practical. Cover committed-then-error, confirmed failure and verification outage.
