## Skeleton ที่ปรับแล้ว

- ครัว: โครงบัตรออเดอร์ รายการอาหาร และบริเวณปุ่มทำอาหาร
- หน้าบิล: โครงบัตรบิล ยอดรวม รายการ และบริเวณรับเงิน
- คำขอบริการ: โครงบัตรคำขอจากโต๊ะ
- ผังโต๊ะ: แทนบล็อกทึบเดิมด้วยโครงเลขโต๊ะ สถานะ และบริเวณปุ่ม
- ฝั่งลูกค้า: โครงข้อมูลร้าน หมวดหมู่ และประวัติออเดอร์ ใช้ร่วมกับ Skeleton เมนูเดิม และไม่แจ้งว่าโต๊ะไม่มีออเดอร์ก่อนโหลดประวัติเสร็จ
- พื้นที่เจ้าของร้านและหน้าเลือกร้าน/คำเชิญ: เพิ่ม loading.tsx สำหรับช่วงรอ Server Component
- Dashboard เมนู รายงาน พนักงาน และตั้งค่า: รักษา Skeleton เดิม เพิ่มข้อความสถานะสำหรับโปรแกรมอ่านหน้าจอ

Skeleton ใช้สี muted ตามธีม ไม่มี emoji หรือสีฉูดฉาด ปิดการเคลื่อนไหวตามการตั้งค่า reduced motion และไม่มีปุ่มหลอกที่กดได้ ข้อมูลเดิมบนหน้าที่ polling จะไม่ถูกแทนด้วย Skeleton ทุกครั้งที่รีเฟรชอัตโนมัติ

คงข้อความและไอคอนหมุนระหว่างส่งออเดอร์ บันทึก รับเงิน และรอ AI เพราะเป็นสถานะการทำรายการ ไม่ใช่การโหลดรายการข้อมูล ยังไม่ได้เพิ่ม animation แชทในรอบนี้

## การตรวจสอบ

- ชุดทดสอบเดิม 190 ข้อผ่าน และ TypeScript ผ่าน
- ตรวจ render ของ Skeleton และหน้ารอใหม่ผ่าน React server renderer แล้ว ไม่พบปุ่มหรือลิงก์ที่ใช้งานได้ในโครงโหลด
- ESLint ของไฟล์ใหม่ผ่าน ส่วนไฟล์เดิมยังมี error Date.now() ระหว่าง render ใน components/order-board.tsx และ warnings ที่พบในการตรวจรอบก่อน
- ยังไม่ได้ทดสอบผ่านเบราว์เซอร์จริงบนมือถือ หรือยืนยัน production build รอบนี้
- ยังไม่ได้ commit, push หรือ deploy การเปลี่ยนแปลงชุดนี้

## ลำดับ 1: โควตาอัปโหลดร่วมกัน

- API อัปโหลด, API เพิ่มเมนู และ Server Action แก้เมนู ใช้ reserveUploadQuota ใน lib/upload-policy.ts และตัวนับบัญชีเดียวกัน
- เจ้าของร้าน 10 ครั้ง/60 วินาที และ 100 ครั้ง/24 ชั่วโมง; บัญชีก่อนสร้างร้านยังใช้เพดานเดิมเฉพาะโลโก้
- การเพิ่ม/แก้เมนูที่ไม่แนบรูปไม่หักโควตา รูปที่ไม่ผ่านการตรวจชนิด/ขนาดหรือ Storage ล้มเหลวหลังจองโควตายังคงนับ
- จำกัด stream ของ multipart เพิ่มเมนู และ JSON เพิ่มเมนู รวมถึงตรวจขนาด FormData ใน action โดยคงข้อจำกัด transport ของ Next.js เดิม
- API แจ้ง 429 พร้อม Retry-After; Server Action ส่ง status และ retryAfter ในผลลัพธ์ ข้อความภาษาไทยแสดงในแบบฟอร์มเดิมได้
- ชุดทดสอบทั้งหมด 200 ข้อผ่าน รวม 10 กรณีใหม่สำหรับโควตาข้ามช่องทาง; TypeScript และ lint ของไฟล์ในลำดับ 1 ผ่าน
- ตรวจ SQL ของตัวนับบนตารางชั่วคราวใน PostgreSQL แล้ว rollback ผ่าน ไม่เปลี่ยนข้อมูลแอป ไม่ต้องเพิ่ม migration หรือ environment variable
- ยังไม่ได้ commit, push หรือ deploy งานชุดนี้ และยังไม่ได้ทดสอบอัปโหลดจริงผ่าน Vercel

## ลำดับ 2: แยกตะกร้าตามหมายเหตุ

- แต่ละรายการมี lineId ของตัวเอง เพิ่ม–ลดจำนวน แก้หมายเหตุ และนำออกได้แยกกัน แม้เป็นเมนูเดียวกัน
- ตอนเพิ่มรายการจากรายละเอียดเมนู ปุ่มเพิ่มด่วน หรือแชทบอท จะรวมจำนวนเฉพาะเมนูและหมายเหตุที่ตรงกัน โดยไม่นับช่องว่างหัวท้าย
- การแก้หมายเหตุในตะกร้าไม่รวมแถวอัตโนมัติ เพื่อรักษาตำแหน่งช่องกรอกและจำนวนของแต่ละรายการ
- ตะกร้าเก่าที่ไม่มี lineId เปิดต่อได้ รักษาลำดับ จำนวน หมายเหตุ และ requestId ของคำขอที่รอยืนยันไว้ ไม่ตัดเมนูซ้ำระหว่างโหลดตะกร้า
- คงเพดาน 50 รายการ และ 99 ชิ้นต่อรายการ หากเพิ่มไม่ได้จะแสดงข้อความและเก็บหน้ารายละเอียดเมนูกับหมายเหตุไว้
- ส่งไป API เฉพาะข้อมูลสั่งอาหารเดิม ไม่ส่ง lineId; API เดิมรองรับเมนูซ้ำคนละหมายเหตุอยู่แล้ว ไม่ต้องแก้ฐานข้อมูล
- เพิ่ม regression tests 10 กรณี ครอบคลุมการรวม/แยกหมายเหตุ การแก้/ลบเฉพาะแถว ตะกร้าเดิม ขีดจำกัด กดเพิ่มติดกัน การโหลดใหม่ และการส่งซ้ำหลังไม่ได้รับคำตอบ
- ชุดทดสอบทั้งหมด 210 ข้อผ่าน, TypeScript ผ่าน, ESLint ของไฟล์ที่แก้ในลำดับนี้ผ่าน และ git diff --check ผ่าน
- ทดสอบ handler ของหน้าและ API ด้วยข้อมูลจำลอง ยังไม่ได้ทดสอบผ่านเบราว์เซอร์จริงหรือยืนยัน production build รอบนี้
- ยังไม่ได้ commit, push หรือ deploy งานชุดนี้

## ลำดับ 3: จำกัดขนาดคำขอแชทระหว่างอ่านข้อมูล

- API แชทใช้ readLimitedJson ร่วมกับคำขอส่วนอื่น อ่าน stream ทีละส่วนและยกเลิกการอ่านเมื่อเกินเพดาน แทนการอ่าน req.text() ทั้งหมดก่อนตรวจ
- คงขนาดสูงสุดเดิม 24,000 ไบต์ รวม JSON และประวัติสนทนา โดยนับจำนวนไบต์จริง ไม่ใช่จำนวนตัวอักษร
- ไม่พึ่ง Content-Length เพียงอย่างเดียว: แม้ไม่ส่งหรือแจ้งขนาดต่ำกว่าจริง ก็ยังถูกจำกัดตามข้อมูลที่อ่านได้
- ขนาดเกินตอบ 413, JSON หรือ Content-Length ผิดรูปแบบตอบ 400, Content-Type ที่ไม่ใช่ application/json ตอบ 415; หน้าแชทส่งชนิดข้อมูลถูกต้องอยู่แล้ว
- ปฏิเสธคำขอที่ไม่ผ่านก่อนเข้าฐานข้อมูล ใช้โควตา หรือเรียก Gemini และยังส่ง Cache-Control: private, no-store
- คงการตรวจ QR, จำนวน/ความยาวข้อความ, โควตา และการตรวจ session ซ้ำหลัง AI ตอบตามเดิม
- เพิ่ม regression tests 7 กรณี ครอบคลุมการหยุดอ่านและยกเลิก stream, header ปลอม/ขาดหาย, UTF-8 ภาษาไทยที่ถูกแบ่งกลางตัวอักษร, ขอบเขต 24,000 ไบต์ และประวัติแชทปกติ 9 ข้อความ
- ชุดทดสอบทั้งหมด 217 ข้อผ่าน, TypeScript ผ่าน, ESLint ของไฟล์ที่แก้ในลำดับนี้ผ่าน และ git diff --check ผ่าน
- ใช้ stream และ AI provider จำลองในการทดสอบ ยังไม่ได้ทดสอบผ่าน Vercel หรือ production build และยังไม่ได้ commit/push/deploy

## ลำดับ 4: แก้ lint error และ warnings เดิม

- แก้ 1 error และ 10 warnings เดิม โดยไม่ปิดหรือลดระดับกฎ ESLint เพิ่ม
- หน้าครัวเก็บเวลาปัจจุบันใน state และอัปเดตตามรอบ polling แทน Date.now() ระหว่าง render; เวลารอยังเดินต่อแม้โหลดข้อมูลครั้งถัดไปล้มเหลว
- การตั้งค่าเสียงของครัว/คำขอบริการใช้ useSyncExternalStore ร่วมกับ localStorage รองรับค่าเริ่มต้นฝั่ง server, การเปลี่ยนจากอีกแท็บ, ค่าเสียงที่ไม่ถูกต้อง และการใช้งานในหน่วยความจำเมื่อบันทึกไม่ได้
- การตรวจหน้าจอมือถือใช้ matchMedia พร้อมสมัคร/ยกเลิก listener และมีค่าเริ่มต้นสำหรับ server ที่สอดคล้องกับการ hydrate
- หน้าเมนูโหลดข้อมูลใน effect ของตัวเอง ใช้ค่าหมวดหมู่ล่าสุดและไม่อัปเดต state จากผลโหลดหลังออกหน้า
- Dashboard/รายงานแยกสถานะรีเฟรชที่เริ่มจากการกดปุ่ม และยกเลิกการเริ่มโหลดที่รออยู่ได้เมื่อออกหน้า; รายงานยังยกเลิกคำขอเก่าเมื่อเปลี่ยนช่วงเวลา
- Slug แสดงสถานะตามค่าที่กำลังตรวจ กันผลลัพธ์เก่าทับชื่อใหม่ และไม่ค้าง checking เมื่อข้อความใหม่ถูกจัดรูปแบบแล้วได้ slug เดิม
- เอา eslint-disable ที่ไม่ได้ใช้ในหน้าตั้งค่าออก และตัดตัวแปรที่ไม่ได้ใช้ในปุ่มออกจากระบบ โดยยังบังคับ type="button" เพื่อให้ผ่านการยืนยันก่อนออกจากระบบ
- ESLint ทั้งโปรเจกต์ผ่านด้วย --max-warnings=0 (0 errors, 0 warnings), TypeScript ผ่าน และ git diff --check ผ่าน
- ชุดทดสอบทั้งหมด 224 ข้อผ่าน รวม 7 กรณีใหม่; หลังปรับ guard Slug ขั้นสุดท้าย รันทดสอบ settings 8 ข้อและ lint ของไฟล์ที่เกี่ยวข้องซ้ำผ่าน
- ยังไม่ได้ทดสอบผ่านเบราว์เซอร์จริงหรือยืนยัน production build และยังไม่ได้ commit/push/deploy

## ลำดับ 6: สรุปยอดรับเงินจริงตามวันรับ

- หน้ารายงานแสดงยอดรับเงินรวม เงินสด และเงินโอน พร้อมจำนวนรายการรับเงินและตารางแยกวัน/เดือนตามช่วงเวลาที่เลือก ใช้ไอคอนและสี muted พร้อม Skeleton ของส่วนใหม่
- อ้างอิง bill_payments.created_at ตามเวลาไทย และรวม amount_cents ซึ่งเป็นยอดหลังหักเงินทอน ไม่ใช้ยอดเงินสดที่ลูกค้ายื่นก่อนทอน
- การรับเงินครั้งเดียวสำหรับหลายออเดอร์นับครั้งเดียว การรับเงินเพิ่มภายหลังในบิลเดิมนับเป็นรายการใหม่ตามวันรับ
- แยกส่วนยอดขายตามวันที่สั่งไว้ตามเดิม รวมออเดอร์ที่ยังไม่ชำระและไม่รวมออเดอร์ยกเลิก ไม่เปลี่ยนความหมายของกราฟ/เมนูขายดี
- CSV เพิ่มส่วนยอดรับเงินจริง เงินสด เงินโอน ยอดรวม และจำนวนรายการ พร้อมยอดรวมของช่วงเวลา แสดงจำนวนเงินสองตำแหน่ง
- คำสั่งอ่านรายการรับเงินกรองร้านและช่วงเวลาในฐานข้อมูล ใช้ขอบเขตเริ่มต้นรวมและสิ้นสุดไม่รวม เพื่อรองรับ timestamp ที่ละเอียดกว่ามิลลิวินาที อ่านเฉพาะวิธีชำระ จำนวนเงิน และวันรับ
- เจ้าของร้านเท่านั้นที่อ่านรายงานได้ ไม่รับ storeId จากผู้เรียกมาใช้กำหนดสิทธิ์ และไม่ส่งชื่อผู้รับเงิน/รหัสรายการชำระออกไปในรายงาน
- ออเดอร์เก่าที่มีสถานะ paid แต่ไม่มีรายการรับเงิน จะไม่ถูกสร้างวันที่หรือวิธีชำระขึ้นเอง มีคำอธิบายในหน้าและ CSV; รายงานนี้แสดงรายการรับเงิน ไม่ใช่บัญชีเงินคืน
- ใช้ตารางเดิม ไม่ต้องเพิ่ม migration, environment variable หรือแก้ข้อมูลร้านจริง
- เพิ่ม tests 8 กรณี; ทั้งชุด 232 ข้อผ่าน, TypeScript ผ่าน, ESLint ทั้งโปรเจกต์ผ่านด้วย --max-warnings=0 และ git diff --check ผ่าน
- ตรวจ SQL ที่สร้างจาก route จริงบน PostgreSQL ผ่านตารางชั่วคราวและ rollback แล้ว ครอบคลุมช่วงเวลาไทย/รอยต่อระดับ microsecond และการแยกร้าน
- ตรวจ render ส่วนรายงานใหม่ผ่าน React server renderer แล้ว ยังไม่ได้ตรวจด้วยเบราว์เซอร์จริงหรือ production build และยังไม่ได้ commit/push/deploy

## ลำดับ 7: ลดข้อมูลที่อ่านและแสดงสถานะอัปเดต

- รายงานกรองออเดอร์ตามร้านและช่วงเวลาที่เลือกในฐานข้อมูลก่อนอ่านรายการอาหาร
- Dashboard อ่านเฉพาะออเดอร์ 7 วันสำหรับกราฟ แยกอ่าน 5 ออเดอร์ล่าสุด และใช้ COUNT ในฐานข้อมูลสำหรับจำนวนออเดอร์ทั้งหมด จึงไม่เปลี่ยนความหมายยอดรวมตลอดอายุร้าน
- หน้าบิลอ่านเฉพาะ id, storeId, tableNumber, sessionToken, createdAt เพื่อจัดกลุ่ม/นับหน้า จากนั้นอ่านข้อมูลออเดอร์เต็มและรายการอาหารเฉพาะบิลในหน้าที่แสดง ไม่มีการจำกัดจำนวนออเดอร์กลางบิล
- ข้อจำกัด: ยังอ่านข้อมูลย่อประวัติของร้านเพื่อจัดกลุ่มบิลและนับหน้า ไม่ใช่ pagination ของกลุ่มบิลทั้งหมดใน SQL; ไม่เพิ่มตารางหรือ migration ในรอบนี้
- หน้าบิล ครัว คำขอบริการ และ Dashboard พัก polling เมื่อแท็บซ่อนหรือเบราว์เซอร์ออฟไลน์ และเรียกอ่านข้อมูลใหม่เมื่อกลับมาเห็นแท็บหรือได้รับ online event พร้อมถอด listener/timer เมื่อออกหน้า
- เพิ่มเวลาโหลดสำเร็จล่าสุดตามเวลาไทยและข้อความออฟไลน์/อัปเดตไม่สำเร็จในหน้าข้างต้นและรายงาน เวลาไม่เลื่อนไปข้างหน้าเมื่อโหลดล้มเหลว
- สถานะออนไลน์เป็นสัญญาณจากเบราว์เซอร์ ไม่ใช่การรับประกันว่าติดต่อเซิร์ฟเวอร์ได้ ความล้มเหลวของ API ยังแสดงแยกตามเดิม
- ทั้งชุด 236 tests ผ่าน รวมกรณีตรวจขอบเขตข้อมูลที่อ่าน รายละเอียดเฉพาะหน้าบิล และหยุด/เริ่ม polling; กรณีเดิมที่บิลเดียวมี 207 ออเดอร์ยังผ่าน
- TypeScript, ESLint ทั้งโปรเจกต์ด้วย --max-warnings=0 และ git diff --check ผ่าน
- สร้าง SQL จาก route จริงและตรวจ EXPLAIN บน PostgreSQL ใน read-only transaction ผ่าน ไม่แก้ข้อมูลร้านหรือ schema
- ยังไม่ได้ทดสอบเบราว์เซอร์จริงหรือ production build และยังไม่ได้ commit/push/deploy

## ลำดับ 8: บันทึกการยกเลิกออเดอร์

- เพิ่มหน้าต่างระบุเหตุผล 1–300 ตัวอักษรก่อนยืนยันยกเลิก แสดงบิล/ออเดอร์ที่จะยกเลิก ป้องกันส่งซ้ำและเก็บเหตุผลไว้เมื่อส่งไม่สำเร็จ
- เซิร์ฟเวอร์บันทึก cancelledBy จากบัญชีที่ยืนยันตัวตน, cancelledByLabel จากอีเมลบัญชี (หรือ ID หากไม่มีอีเมล), cancelledAt จากเวลาบนเซิร์ฟเวอร์ และ cancellationReason ที่ตัดช่องว่างหัวท้าย
- ไม่เชื่อถือผู้ดำเนินการ/เวลาที่ส่งมาจาก client; คงการล็อกออเดอร์และตรวจร้าน/บทบาท ไม่อนุญาตครัวยกเลิก หรือยกเลิกหลังรับเงิน/เสิร์ฟ/จบออเดอร์
- คำขอยกเลิกซ้ำไม่เขียนทับเหตุผลหรือผู้ดำเนินการเดิม
- ประวัติในหน้าบิลแสดงผู้ยกเลิก เวลา และเหตุผล; API ลูกค้าและผลการส่งออเดอร์ซ้ำไม่เปิดเผยข้อมูล audit ภายใน
- Migration 0011_order_cancellation_audit สร้างด้วย Drizzle Kit ตามโครงสร้าง repo และเพิ่ม nullable columns 4 ช่องใน Supabase แล้ว ไม่มีการแก้หรือเติมเหตุผลให้ออเดอร์เก่า
- ออเดอร์ยกเลิกเก่าที่ไม่มี audit แสดงว่าไม่มีรายละเอียดการยกเลิกย้อนหลัง; โค้ดใหม่เริ่มบังคับเหตุผลเมื่อ deploy ส่วน API นี้แล้ว
- ตรวจ SQL ด้วยตารางชั่วคราวบน PostgreSQL แล้ว rollback ผ่าน ทั้งค่าเริ่มต้น null และการเก็บผู้ดำเนินการ/เวลา/เหตุผล
- ตรวจ Supabase security advisors แล้ว ไม่พบรายการใหม่จากการเพิ่มคอลัมน์; รายการเดิมคือ RLS ไม่มี policy (10 ตาราง backend-only), สิทธิ์ execute ของ rls_auto_enable สำหรับ anon/authenticated และ leaked password protection ปิดอยู่
- เพิ่ม tests 5 กรณี และเพิ่มการตรวจไม่เปิดเผย audit ใน idempotency test เดิม; ทั้งชุด 241 ข้อผ่าน พร้อมตรวจ idempotency ซ้ำหลังเพิ่ม assertions
- TypeScript และ ESLint ทั้งโปรเจกต์ผ่าน ยังไม่ได้ทดสอบผ่านเบราว์เซอร์จริงหรือ production build
- ยังไม่ได้ commit/push/deploy โค้ด; migration ฐานข้อมูลเพิ่มแล้วและเข้ากันได้กับโค้ดเดิม


## ลำดับ 9: Animation แชทแบบเรียบ

- ข้อความคำถามระหว่างรอ คำตอบล่าสุด และข้อความแจ้งเพิ่มตะกร้า ค่อย ๆ ปรากฏพร้อมเลื่อนขึ้น 4px ใน 180ms
- ใช้จุดสามจุดเปลี่ยนความทึบระหว่างรอคำตอบ พร้อมข้อความสถานะเดิม; จุดเป็นส่วนตกแต่งที่ซ่อนจากโปรแกรมอ่านหน้าจอ
- ปรับหน้าต่างแชทเป็น 200ms และลดการขยาย/ย่อปุ่มเปิดแชทเหลือ 2% พร้อมเอาการหมุนไอคอนออก
- animation ใหม่ทำงานเฉพาะ prefers-reduced-motion: no-preference; โหมดลดการเคลื่อนไหวแสดงจุดและข้อความนิ่ง
- ใช้รหัสข้อความคงที่แทน index เพื่อรักษา DOM ของข้อความเดิมเมื่อตัดประวัติให้เหลือ 20 ข้อความ และให้คำตอบใหม่แสดง animation ต่อได้
- ไม่เพิ่ม dependency, delay จำลองการพิมพ์ หรือคำขอ AI; รหัสข้อความใช้เฉพาะ UI ไม่ถูกส่งไป API
- เพิ่ม regression test เรื่องรหัสข้อความหลังตัดประวัติและฟิลด์ที่ส่ง API; ทั้งชุด 242 ข้อผ่าน TypeScript และ ESLint ทั้งโปรเจกต์ผ่าน
- ตรวจ compile CSS ด้วย Tailwind ผ่าน ทั้ง animation และกฎ reduced motion; ยังไม่ได้ตรวจภาพเคลื่อนไหวผ่านเบราว์เซอร์จริงหรือ production build
- ลำดับนี้ไม่มีการแก้ฐานข้อมูล และยังไม่ได้ commit/push/deploy โค้ด
