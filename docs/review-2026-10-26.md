## 1. ควรแก้ — slug สามารถชนกับ UUID ของร้านอื่น

ระดับ: ปานกลางในแง่การรบกวนการค้นหาร้าน/การใช้งานบาง endpoint ขอบเขตจำกัด ไม่พบการอ่านข้อมูลส่วนตัวหรือรับเงินข้ามร้าน

ตำแหน่ง:
- utils/store.ts: getStoreBySlugOrId ค้นจาก slug ก่อน แล้วค่อยค้น id
- lib/store-validation.ts: slug อนุญาตข้อความรูป UUID และไม่มีการแยก namespace จาก id
- app/api/orders/[id]/route.ts: GET ฝั่งลูกค้าส่ง order.storeId เข้า withCustomerSession ในชื่อ storeSlug
- lib/customer-session.ts: withCustomerSession ใช้ตัวค้นหารวม slug/id

วิธีจำลองในเครื่องด้วย action/route จริงและฐานข้อมูล fixture:
1. ร้าน A มี UUID, โต๊ะรอบปัจจุบัน และออเดอร์ที่ลูกค้ามี QR ถูกต้อง
2. GET รายละเอียดออเดอร์ด้วย token ถูกต้อง ตอบ 200
3. บัญชีใหม่สร้างร้าน B โดยตั้ง slug เป็น UUID ของร้าน A ผ่าน createStoreOnboarding ได้สำเร็จ
4. getStoreBySlugOrId(UUID ของ A) กลับเลือกร้าน B
5. GET ออเดอร์เดิมด้วย token เดิม เปลี่ยนเป็น 403/sessionExpired เพราะไปตรวจโต๊ะของร้าน B
6. GET ประวัติโต๊ะผ่าน slug ปกติ cafe-a ยังตอบ 200

ผลกระทบที่ยืนยัน: ลิงก์/endpoint ที่ค้นด้วย id อาจเลือกร้านผิดหรือใช้ไม่ได้ ขณะที่เส้นทาง slug ปกติยังทำงาน ไม่ได้พิสูจน์การปลอมการชำระเงินหรือการข้าม QR อ่านออเดอร์ร้านอื่น และไม่พบ frontend ปัจจุบันเรียก GET รายละเอียดออเดอร์รายชิ้นนี้โดยตรง

ตรวจฐานข้อมูล production แบบนับจำนวนเท่านั้น: UUID-shaped slugs = 0 และ slug ที่ตรงกับ id ของอีกร้าน = 0 จึงยังไม่พบข้อมูลชนกันจริง ณ เวลาที่ตรวจ

แนวทางแก้:
- แยก getStoreById สำหรับค่ารหัสที่ระบบทราบแน่ชัดออกจาก lookup ด้วย slug โดยเฉพาะการตรวจ session จาก order.storeId
- สงวน slug รูป UUID ที่ onboarding/settings/availability หรือออกแบบ URL ให้แยกชนิดตัวระบุชัดเจน
- ทดสอบกรณีร้าน B ตั้ง slug ตรงกับ id ร้าน A แล้ว lookup ด้วย id ยังได้ A และไม่กระทบ QR ของ A
- ไม่ควรสลับลำดับค้นหาเพียงอย่างเดียวโดยไม่จัดการ slug รูป UUID ที่อาจมีอยู่

## 2. เสริมระดับต่ำ — GET /auth/signout เปลี่ยนสถานะ session

app/auth/signout/route.ts เปิดทั้ง GET และ POST ให้เรียก auth.signOut() จำลอง GET กับ Auth stub แล้วได้ 303 และ signOut ถูกเรียก 1 ครั้ง

จึงมีเส้นทางที่เพียงเปิดลิงก์ก็สั่งออกจากระบบได้ แนะนำให้เปลี่ยนสถานะผ่าน POST เท่านั้น และตรวจแหล่งที่มาของ POST หรือใช้ Server Action ที่เหมาะสม การตรวจนี้ยืนยันพฤติกรรม handler แต่ไม่ได้ทดสอบ logout CSRF ด้วย session จริงในเบราว์เซอร์ ไม่ใช่หลักฐานการขโมยบัญชี

## สิ่งที่ควรเสริมโดยไม่ต้องเพิ่มฟีเจอร์ใหญ่

1. Storage: ตั้ง allowed_mime_types เป็น image/jpeg, image/png, image/webp, image/gif และ file_size_limit เป็น 5 MiB ทั้ง restaurant-logos/menu-photos ตอนนี้ยังเป็น null ทั้งคู่ แอปตรวจครบแล้ว จึงเป็นการป้องกันเพิ่มอีกชั้น ไม่ใช่ช่องทางอัปโหลดสาธารณะที่ข้ามสิทธิ์ได้
2. Storage policies: มี SELECT policy อ่าน menu-photos ซ้ำกัน 2 ตัว และ PUBLIC SELECT บนสอง bucket ทำให้สิทธิ์กว้างถึงการขอรายชื่อ/metadata ของไฟล์ พิจารณาลดเหลือเท่าที่จำเป็นเมื่อใช้ public image URLs; ยังไม่พบว่ามีไฟล์ลับอยู่ใน bucket และไม่ได้ทดลองไล่รายการไฟล์จริง
3. CI: ยังไม่มี .github/workflows ใน repository ให้บังคับรัน lint, TypeScript และ tests ก่อน merge ควรเพิ่มเพื่อไม่ต้องพึ่งการรันทดสอบด้วยมือทุกครั้ง Vercel build success ไม่ทดแทนชุดทดสอบเหล่านี้
4. ประสิทธิภาพ: การแบ่งหน้าบิลยังอ่าน metadata ประวัติของร้านก่อนเลือกหน้า และรายงานดึงออเดอร์ในช่วงเวลามาสรุปในแอป ให้ติดตามเมื่อข้อมูลสะสมมากขึ้น รอบนี้ไม่ได้พบหรือวัดอาการช้าจริง

## สิทธิ์และข้อมูลที่ตรวจ

- Auth: ตรวจ getUser กับ Supabase และอ่านบทบาทจากฐานข้อมูลปัจจุบัน ไม่ใช้ user_metadata ตัดสินสิทธิ์
- Owner/cashier/kitchen: route ที่เขียนข้อมูลตรวจบทบาทและ store scope; ชุดทดสอบครอบคลุมการข้ามร้านและการเปลี่ยนบทบาท
- คำเชิญ: ต้องใช้อีเมลยืนยันแล้วและผู้ใช้กดยอมรับ มี account lock และตรวจสถานะ/บทบาทคำเชิญซ้ำ
- ออเดอร์: ราคาอ่านจากฐานข้อมูล, จำกัดรายการ/จำนวน, ตรวจ QR ปัจจุบัน, มี idempotency และโควตา
- รับเงิน: ตรวจยอด/รายการปัจจุบันใน transaction พร้อมล็อกข้อมูล, ป้องกันรับเงินซ้ำ และไม่ปิดโต๊ะที่ยังค้างยอด/งานครัว/การเสิร์ฟ
- อัปโหลด: ทุกช่องทางใช้ตัวตรวจภาพเดียวกัน, จำกัด bytes/pixels/frames, ตรวจสิทธิ์ก่อนทำงาน และมีโควตาร่วม; ทดสอบด้วย decoder จริงแต่ Storage จำลอง
- แชท: จำกัด payload/history/quota, provider timeout, ตรวจ QR ซ้ำหลังตอบ และไม่มีเครื่องมือเปลี่ยนออเดอร์/รับเงิน; ไม่เรียก Gemini จริงรอบนี้
- XSS/SQL: ทบทวนจุดแสดงข้อความ/คำตอบ AI และ query; dangerouslySetInnerHTML ที่พบใช้สคริปต์ theme คงที่ ไม่พบการใส่ input ผู้ใช้เข้า HTML ตรง ๆ หรือ SQL ดิบจากผู้ใช้ในเส้นทางที่ตรวจ
- Secrets: สแกน pattern Google key, Supabase secret/service-role JWT, GitHub token และ private key ในไฟล์ tracked 262 ไฟล์ ไม่พบ match; .env.local ไม่ถูกติดตาม และ git log ของ .env/.env.local ไม่พบ commit ในประวัติที่มีในเครื่อง นี่ไม่ใช่การสแกน secret ทุกชนิด/ทุก blob ของประวัติ Git

## Supabase production — ตรวจ catalog แบบอ่านอย่างเดียว

- public tables 10 ตารางเปิด RLS
- anon/authenticated ไม่มีสิทธิ์ CRUD ระดับตาราง และไม่มีสิทธิ์ SELECT/INSERT/UPDATE ระดับคอลัมน์ของ 10 ตารางนี้
- public SECURITY DEFINER ที่ตรวจพบคือ rls_auto_enable; anon/authenticated ไม่มี EXECUTE
- Storage objects ไม่มี INSERT/UPDATE/DELETE policy สำหรับ public ในผลที่ตรวจ การอัปโหลด/ลบผ่าน server เป็นผู้ทำ
- RLS no policy: INFO 10 รายการ สอดคล้องกับ backend-only access ไม่ควรเปิด policy กว้างเพื่อล้างคำเตือน
- Leaked password protection: WARN 1 รายการ UI ใช้ Google OAuth แต่ไม่ได้ตรวจ provider settings ทั้งหมด จึงยังไม่สรุปว่า password login เปิดหรือปิด
- Unused index: INFO 8 รายการ รวมดัชนีใหม่/foreign key ไม่ควรลบทันทีจากตัวเลขนี้

## สถานะการแก้ไขหลังตรวจ — จุดที่ 2

แก้ใน working tree แล้ว ยังไม่ได้ push/deploy:

- ลบ GET handler ของ /auth/signout: Next.js ตอบ GET/HEAD เป็น 405 โดยไม่เรียก signOut; OPTIONS อนุญาตเฉพาะ OPTIONS และ POST
- POST ต้องมี Origin ตรงกับ protocol ของ request URL และ Host ฝั่งเบราว์เซอร์ ถ้าไม่มี Origin, เป็น null, ผิดโดเมน/พอร์ต/protocol หรือ Sec-Fetch-Site ระบุข้าม origin จะปฏิเสธ 403 ก่อนสร้าง Auth client
- ไม่ใช้ X-Forwarded-Host/Proto ที่ส่งเข้ามาเพื่ออนุญาตคำขอหรือกำหนด redirect; รองรับ Host ของ localhost, LAN, IPv6 และ Vercel แม้ Next.js ใช้ bind address ภายใน
- POST ที่ถูกต้องยังเรียก Supabase signOut และ redirect 303 ไป /owner/login พร้อม private, no-store; ไม่เปลี่ยน scope การ sign out เดิม
- Auth ล้มเหลวตอบ 503 พร้อมข้อความทั่วไป ไม่ redirect เหมือนสำเร็จและไม่ส่งรายละเอียดภายใน
- LogoutButton ทุกหน้าส่งฟอร์ม POST อยู่แล้ว จึงไม่เปลี่ยน UI; เพิ่มทดสอบฟอร์มจริงของ component ว่าต้องยืนยันก่อน submit และป้องกันการกดซ้ำ
- เพิ่ม tests/signout.test.mjs จำนวน 7 tests โดยใช้ตัว dispatch HTTP methods ของ Next.js ที่ติดตั้งจริง และจำลอง Supabase Auth; เพิ่ม 1 test ใน tests/dialogs.test.mjs
- รอบนี้ไม่ได้เรียกออกจากระบบด้วย session จริงบน production และไม่ได้เปลี่ยนการตั้งค่า Supabase
